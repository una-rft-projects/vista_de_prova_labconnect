1. Entendendo a situação-problema

A universidade controla oficinas, professores, laboratórios, equipamentos e participantes em uma única planilha. Isso gera dados repetidos e campos com listas como “Arduino; Sensor; Motor”. Nossa tarefa é separar corretamente os conceitos e relacioná-los.

5 entidades principaisProfessor, Laboratório, Oficina, Equipamento, Participante
2 tabelas associativasOficina_Equipamento e Oficina_Participante
7 tabelas ao finalEstrutura relacional sugerida em 3FN
Observação: o enunciado não exige nomes de atributos ou identificadores exatamente iguais aos deste gabarito. Outras soluções equivalentes são válidas se respeitarem as regras de negócio.

2. DER — entidades e cardinalidades

Diagrama abaixo em estilo lógico simplificado. PK identifica a chave primária; FK, a chave estrangeira. As duas relações N:N foram resolvidas por entidades associativas.

Regra do enunciadoCardinalidadeComo implementar
Um professor ministra várias oficinas; cada oficina tem um professor.Professor 1:N Oficinaoficina.id_professor (FK)
Um laboratório recebe várias oficinas; cada oficina ocorre em um laboratório.Laboratório 1:N Oficinaoficina.id_laboratorio (FK)
Uma oficina usa vários equipamentos; um equipamento pode estar em várias oficinas.Oficina N:N Equipamentooficina_equipamento
Uma oficina tem vários participantes; um participante pode frequentar várias oficinas.Oficina N:N Participanteoficina_participante

Detalhe importante: um N:N é representável diretamente em um DER conceitual, mas ao transformar para tabelas relacionais é necessário criar uma tabela associativa.

3. Normalização: da planilha à 3FN

1FN — Primeira Forma Normal

Um campo deve conter um valor atômico, e não uma lista. Em vez de gravar "Arduino; Sensor; Motor" em uma única célula de equipamentos, cada associação entre uma oficina e um equipamento será registrada individualmente. A mesma regra vale para participantes.

2FN — Segunda Forma Normal

Além de estar na 1FN, cada atributo não-chave deve depender de toda a chave candidata, não apenas de parte de uma chave composta. Em associações como (id_oficina, id_equipamento), não devemos guardar nome_oficina ou descricao_equipamento: esses atributos dependem somente de um dos IDs, não do par completo.

3FN — Terceira Forma Normal

Além da 2FN, removemos dependências transitivas de atributos não-chave em relação às chaves. Por exemplo, id_oficina → id_professor → nome_professor. Assim, nome e e-mail ficam na tabela professor; a oficina conserva apenas id_professor.

Problema da planilhaCorreçãoBenefício
Professor e e-mail repetidos por oficinaTabela professor + FK em oficinaAtualização em um único lugar
Equipamentos em texto separado por “;”equipamento + oficina_equipamentoRelação pesquisável e sem listas
Participantes no mesmo campoparticipante + oficina_participanteCPF, nome e e-mail próprios
Nome do laboratório duplicadolaboratorio + FK em oficinaEvita inconsistências

4. Modelo relacional final

As tabelas abaixo são o resultado da conversão do DER para o modelo lógico e físico.

TabelaCampos e chaves
professorid_professor PK, cpf UNIQUE, nome, email UNIQUE
participanteid_participante PK, cpf UNIQUE, nome, email UNIQUE
laboratorioid_laboratorio PK, nome UNIQUE
equipamentoid_equipamento PK, descricao, numero_patrimonio UNIQUE
oficinaid_oficina PK, nome, data_oficina, carga_horaria CHECK (> 0), id_professor FK, id_laboratorio FK
oficina_equipamentoid_oficina PK/FK, id_equipamento PK/FK
oficina_participanteid_oficina PK/FK, id_participante PK/FK
A chave primária composta das tabelas associativas impede que a mesma pessoa seja vinculada duas vezes à mesma oficina, ou que um mesmo equipamento seja associado duas vezes a ela. As FKs impedem referências a registros inexistentes.

5. SQL MySQL — solução completa e executável

O script cria as sete tabelas, aplica AUTO_INCREMENT, PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE e CHECK, cadastra dados de teste e executa a consulta final. Recomendado: MySQL 8.0.16 ou superior para aplicação efetiva de CHECK.

CREATE DATABASE IF NOT EXISTS labconnect
  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE labconnect;

CREATE TABLE professor (
  id_professor INT AUTO_INCREMENT PRIMARY KEY,
  cpf CHAR(11) NOT NULL UNIQUE,
  nome VARCHAR(120) NOT NULL,
  email VARCHAR(150) NOT NULL UNIQUE
);

CREATE TABLE participante (
  id_participante INT AUTO_INCREMENT PRIMARY KEY,
  cpf CHAR(11) NOT NULL UNIQUE,
  nome VARCHAR(120) NOT NULL,
  email VARCHAR(150) NOT NULL UNIQUE
);

CREATE TABLE laboratorio (
  id_laboratorio INT AUTO_INCREMENT PRIMARY KEY,
  nome VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE equipamento (
  id_equipamento INT AUTO_INCREMENT PRIMARY KEY,
  descricao VARCHAR(160) NOT NULL,
  numero_patrimonio VARCHAR(40) NOT NULL UNIQUE
);

CREATE TABLE oficina (
  id_oficina INT AUTO_INCREMENT PRIMARY KEY,
  nome VARCHAR(160) NOT NULL,
  data_oficina DATE NOT NULL,
  carga_horaria INT NOT NULL,
  id_professor INT NOT NULL,
  id_laboratorio INT NOT NULL,
  CONSTRAINT chk_carga_horaria CHECK (carga_horaria > 0),
  CONSTRAINT fk_oficina_professor FOREIGN KEY (id_professor)
    REFERENCES professor(id_professor),
  CONSTRAINT fk_oficina_laboratorio FOREIGN KEY (id_laboratorio)
    REFERENCES laboratorio(id_laboratorio)
);

CREATE TABLE oficina_equipamento (
  id_oficina INT NOT NULL,
  id_equipamento INT NOT NULL,
  PRIMARY KEY (id_oficina, id_equipamento),
  FOREIGN KEY (id_oficina) REFERENCES oficina(id_oficina),
  FOREIGN KEY (id_equipamento) REFERENCES equipamento(id_equipamento)
);

CREATE TABLE oficina_participante (
  id_oficina INT NOT NULL,
  id_participante INT NOT NULL,
  PRIMARY KEY (id_oficina, id_participante),
  FOREIGN KEY (id_oficina) REFERENCES oficina(id_oficina),
  FOREIGN KEY (id_participante) REFERENCES participante(id_participante)
);

-- Consulta pedida: uma linha por oficina, reunindo os equipamentos
SELECT
  o.nome AS oficina,
  p.nome AS professor,
  l.nome AS laboratorio,
  COALESCE(
    GROUP_CONCAT(DISTINCT e.descricao ORDER BY e.descricao SEPARATOR ', '),
    'Nenhum equipamento'
  ) AS equipamentos
FROM oficina AS o
JOIN professor AS p ON p.id_professor = o.id_professor
JOIN laboratorio AS l ON l.id_laboratorio = o.id_laboratorio
LEFT JOIN oficina_equipamento AS oe ON oe.id_oficina = o.id_oficina
LEFT JOIN equipamento AS e ON e.id_equipamento = oe.id_equipamento
GROUP BY o.id_oficina, o.nome, p.nome, l.nome
ORDER BY o.id_oficina;
Para repetir o script no mesmo banco sem conflito, apague antes o banco labconnect de testes ou ajuste os identificadores e inserts. Não execute comandos destrutivos em bancos de produção.

6. Resultado esperado da consulta

Uma linha por oficina. GROUP_CONCAT reúne descrições vindas de múltiplas linhas; LEFT JOIN preserva uma oficina mesmo se ela ainda não tiver equipamento associado.

7. Erros frequentes e como corrigir

Confundir 1:N com N:N
Uma oficina tem um único professor e um único laboratório, portanto as FKs pertencem a oficina. Já oficinas e equipamentos, assim como oficinas e participantes, são N:N: exigem duas tabelas associativas.
Colocar id_oficina diretamente em participante ou equipamento
Isso limita cada participante ou equipamento a apenas uma oficina, contradizendo as regras de negócio.
Escrever INSERT dentro do CREATE TABLE
CREATE TABLE define colunas e restrições. INSERT INTO é um comando separado, usado para registrar linhas depois que a tabela existe.
Declarar o nome da tabela como chave primária
Uma PK é uma coluna ou conjunto de colunas: id_oficina INT AUTO_INCREMENT PRIMARY KEY, por exemplo.
Fazer JOIN diretamente de oficina para equipamento
O caminho certo é oficina → oficina_equipamento → equipamento. A consulta final precisa dessa tabela intermediária.
Descrever a 2FN ou a 3FN apenas como “separar tabelas”
A 2FN trata de dependências parciais da chave; a 3FN elimina dependências transitivas. É importante justificar com exemplos dos próprios dados.

9. Três perguntas para revisar com a turma

1. Por que a tabela oficina_equipamento utiliza duas chaves estrangeiras que juntas formam sua chave primária?
2. O que acontece se o e-mail de um professor for armazenado em cada oficina e ele precisar alterá-lo?
3. Por que a consulta final precisa de GROUP_CONCAT e GROUP BY para mostrar uma linha por oficina?
Ver respostas comentadas

1. A combinação representa um vínculo exclusivo, evitando repetições, e as FKs garantem que oficina e equipamento existam.

2. Seriam necessárias várias atualizações, com risco de inconsistência — anomalia de atualização.

3. Um JOIN com os equipamentos gera potencialmente várias linhas por oficina; o agrupamento reúne essas linhas e a função concatena as descrições apenas na apresentação.
